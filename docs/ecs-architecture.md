# Архитектура ECS Continuum

ECS хранит состояние игрового мира и выполняет системы, изменяющие это состояние. Компоненты содержат данные, системы — поведение.

Текущая реализация последовательная и однопоточная. Будущие расширения описаны отдельно.

## 1. Модель данных

Используется сочетание отдельных хранилищ компонентов и архетипов для поиска сущностей.

| Элемент | Назначение |
|---|---|
| `World` | Владеет сущностями, хранилищами компонентов, архетипами, кэшем запросов и выполнением систем |
| `Entity` | Идентификатор сущности: `index` и `generation` |
| `Stash<T>` | Хранит значения компонента `T` и обеспечивает доступ по `Entity` |
| `Archetype` | Хранит набор типов компонентов и список соответствующих сущностей |
| `Query` | Описывает выборку сущностей по компонентам |
| `QueryView` | Обеспечивает временный обход результатов запроса |

Значения компонентов находятся только в `Stash<T>`. Архетипы хранят принадлежность сущностей к наборам компонентов.

`Stash<T>` использует плотные массивы сущностей и компонентов с дополнительным индексом для поиска. Удаление переносит последний элемент на освободившееся место.

Основные инварианты:

- Каждая живая сущность принадлежит ровно одному архетипу.
- Набор компонентов сущности совпадает с сигнатурой её архетипа.
- У сущности может быть только один компонент каждого типа.
- При повторном использовании индекса меняется `generation`, поэтому старый идентификатор становится недействительным.
- `Entity` используется только в своём `World`. Для сохранения сцены нужны отдельные постоянные идентификаторы.
- `ComponentID` назначается внутри мира и не используется как постоянный идентификатор типа.

Перемещение, перемещающее присваивание и разрушение компонентов не должны бросать исключения. Текущий `add` также требует копирования переданного значения.

## 2. Запросы и время жизни

Запрос задаёт обязательные компоненты через `with<T>` и исключённые через `without<T>`. Один тип нельзя одновременно требовать и исключать.

Кэш запроса содержит подходящие архетипы и обновляется при появлении новых. Сам `Query` можно сохранять в системе.

`QueryView` создаётся на время обхода. Пока существует хотя бы один `QueryView` мира, запрещены применение структурных изменений и регистрация новых запросов. Порядок обхода сущностей не гарантируется.

`get` предоставляет чтение компонента, `getMut` — изменение его данных. При отсутствии компонента возвращается `nullptr`.

Указатели на компоненты нельзя сохранять через структурные изменения или `commit`: массивы могут переместиться. Сохранённые ссылки на мир и его хранилища действительны только до уничтожения мира.

## 3. Системы и владение

Система — класс, реализующий `ISystem`.

| Метод | Назначение |
|---|---|
| `awake(World&)` | Получить доступ к миру, подготовить запросы и состояние системы |
| `update(float deltaTime)` | Выполнить обновление; время передаётся в секундах |
| `destroy()` | Завершить работу системы |

Мир не вычисляет время: `deltaTime` передаёт вызывающая сторона.

Пользователь создаёт группы через `World::createSystemGroup()` и регистрирует системы через `SystemGroup::registerSystem<T>()`. Сейчас система создаётся без аргументов конструктора.

`World` владеет закрытым `ExecutionLayer`. Слой владеет группами, группы — экземплярами систем. Копирование и перемещение мира запрещены.

`WorldExecution` хранит ссылку на мир и предоставляет `awake`, `update`, `destroy`. Сейчас приложение вызывает их явно. Разрушение обёртки или мира не заменяет вызов `destroy()`.

Порядок выполнения:

1. До первого `awake` разрешено создавать группы и регистрировать системы.
2. Перед инициализацией регистрация закрывается сразу во всех группах.
3. `awake` и `update` выполняются в порядке регистрации групп и систем.
4. `destroy` выполняется в обратном порядке только для систем, успешно завершивших `awake`.

Повторный `awake` запрещён. После успешного завершения повторный `destroy` ничего не делает.

## 4. Структурные изменения

Структурные операции — создание и уничтожение сущности, добавление и удаление компонента.

Пользователь всегда вызывает обычные методы:

- `World::createEntity()`;
- `World::destroyEntity()`;
- `Stash<T>::add()`;
- `Stash<T>::remove()`.

Способ выполнения выбирается внутри ECS:

| Контекст | Поведение |
|---|---|
| Вне выполнения систем, без активных `QueryView` | Изменение применяется сразу |
| Внутри `awake`, `update` или `destroy` системы | Изменение записывается в буфер |
| Вне выполнения систем, при активном `QueryView` | Структурная операция запрещена |

Сам по себе `QueryView` не включает отложенный режим.

Изменение полей существующего компонента через `getMut` происходит сразу. Запросы и проверки наличия компонентов отражают уже применённую структуру мира.

При отложенном создании `Entity` возвращается сразу, но находится в состоянии `Reserved`. На него можно записывать дальнейшие команды, однако до применения создания он отсутствует в запросах и `hasEntity` возвращает `false`.

## 5. Commit и буфер команд

`ExecutionLayer` владеет одним переиспользуемым `CommandBuffer`. Внутренний `Commands` направляет в него операции; пользователь не получает этот объект.

Буфер хранит команды и собственные копии добавляемых компонентов.

`World::commit()` применяет все накопленные структурные изменения:

- Автоматический вызов выполняется после каждой группы, включая последнюю, во время `awake`, `update` и `destroy`.
- Между системами одной группы автоматического вызова нет.
- Система может вызвать `commit` вручную после завершения всех активных `QueryView` этого мира.
- Ручной вызов применяет также команды предыдущих систем текущей группы.
- После ручного вызова запись новых команд продолжается.
- Вложенный `commit` и запись структурных команд во время применения запрещены.
- Вне выполнения систем, при отсутствии активных `QueryView`, вызов ничего не делает.

Команды группируются по полному `Entity`. Группы обрабатываются в порядке первого появления в буфере; внутри группы учитывается порядок команд.

Для каждой сущности вычисляется итоговый набор компонентов, после чего выполняется не более одного перехода между архетипами. Новая сущность сразу попадает в итоговый архетип.

Правила обработки:

- Повторное добавление имеющегося компонента не заменяет значение.
- Удаление отсутствующего компонента ничего не меняет.
- Удаление с последующим добавлением заменяет компонент.
- Уничтожение сущности отменяет дальнейшие команды для неё.
- Создание с последующим уничтожением до `commit` отменяет создание.
- Команды для недействительных идентификаторов игнорируются.

## 6. Ошибки

ECS передаёт исключения вызывающей стороне. При прерванном выполнении группы или ошибке применения оставшиеся команды очищаются, неиспользованные резервирования сущностей освобождаются.

Полного отката нет: изменения данных компонентов и уже применённые структурные изменения сохраняются.

Ошибка инициализации или завершения переводит выполнение в `Failed`, из которого разрешён `destroy`. Ошибка обновления сейчас сохраняет состояние `Ready`; решение о продолжении принимает вызывающая сторона.

Группа учитывает успешно инициализированные системы. При ошибке завершения повторный `destroy` продолжает оставшиеся вызовы. Уже вызванный метод повторно не выполняется, отброшенные команды не восстанавливаются.

## 7. Дальнейшее развитие

Следующие возможности пока не реализованы:

1. **Интеграция с движком.** Движок подключает `WorldExecution` к запуску, обновлению и завершению приложения. Пользователь продолжает работать через `World`, группы и системы.
2. **Общие ресурсы.** Определяется доступ систем к времени, вводу и другим данным вне компонентов с явным владением и временем жизни.
3. **Зависимости систем.** Системы объявляют порядок выполнения и чтение или запись компонентов и ресурсов. На этой основе строится план выполнения.
4. **Параллельное выполнение.** Совместимые системы одной группы могут выполняться одновременно. Группа завершается общим `commit` после окончания всех её задач.
5. **Оптимизация по измерениям.** Улучшаются хранение, запросы и применение команд только после выявления конкретных затрат.

Для параллельного выполнения сохраняется модель одного общего буфера. Потребуются синхронизация записи команд и их данных, резервирования сущностей и регистрации типов.

Порядок применения должен задаваться планом выполнения, а не скоростью потоков. Защита буфера не защищает прямую запись в компоненты: такие конфликты предотвращает планировщик.

Ручной `commit` при параллельном выполнении потребует остановки всех задач, работающих с миром. До появления такого механизма он допустим только в последовательном контексте.
